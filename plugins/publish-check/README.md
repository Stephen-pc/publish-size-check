# publish-check

发布尺寸检查——对照目标平台的几何规格，检查文件能不能发、哪一项参数过不了。

**只查几何参数。不查内容合规。**

## 这个插件解决什么问题

发图这一步最容易翻车的地方不是内容，是**尺寸**：

- 出图时选了个「通用 1024×1024」，投小红书才发现要 3:4
- 图里写着 300dpi，印出来只有 68mm 宽（dpi 字段达标 ≠ 实际够印）
- 一次发九张，单张都合规但尺寸不齐，页面跳动

本插件只回答一个问题：**这个文件的尺寸参数，能不能过目标平台的要求？过不了的是哪一项？**

只诊断，不改文件。原件全程只读。

## 查什么 / 不查什么

| 查 | 不查 |
|---|---|
| 像素尺寸、宽高比 | ❌ 内容是否违规、涉政涉黄 |
| dpi、实际印刷宽度 | ❌ 是否含二维码/联系方式 |
| 文件体积、格式 | ❌ 文字占画面比例 |
| 色彩模式要求 | ❌ 字体版权、图片版权、商标 |
| 多图尺寸一致性 | ❌ 医疗/金融等行业的资质标识 |

**不查的那些不是不重要，是本插件做不到。** 它只做几何参数计算——正因为范围窄，才能做到零依赖、结果确定、不会误判内容。

## 两种触发方式

**① 直接问** —— 你给了文件并问到发布尺寸：

> 「这图发小红书会不会糊」「平台要多大尺寸」「dpi 够吗」「投稿插图够不够清晰」「被退回来说分辨率不够」

**② 寄生自检（覆盖面最大的用法）** —— 出图流程结束后自动跑，你不需要知道这个插件存在：

```
你: 帮我做一张小红书封面
  ↓
[出图技能] 生成封面文件
  ↓
★ 有文件落盘 + 你提到了发布平台 → 自动体检
  ↓
"封面已生成：1242×1660。顺带确认过小红书规格，可以直接发。"
```

汇报是**分级**的：通过就一句话带过，有问题才展开细节并**给出替代方案**。没要求体检时，不会甩一份 30 行诊断打断体验。

## 核心能力

### dpi 达标 ≠ 可用

投稿和印刷的合格判据是「**最终尺寸下的 dpi**」，不是文件里的 dpi 元数据。

一张 800×600 像素、标着 300dpi 的图，dpi 字段完全达标，但印出来只有 **68mm 宽**，达不到单栏 88mm 的要求。**改 dpi 数字不会增加一个像素**，这种图必须从源文件重新导出。

插件用 `像素数 ÷ dpi × 25.4 = 实际印刷宽度(mm)` 判定，并与期刊常用栏宽比对。

### 多图连发：指出改哪一张

单张全达标但整组不整齐，是最常见的翻车方式。组级结论不会说"三张都不一致"，而是**指出少数派是哪一张**：

```
>> 结论: 这一组的主因是 cover3.png 的尺寸和其余不一致……
         统一按同一规格重导一遍即可，不用逐张处理。
```

用户拿到的不是"三张都有问题"，而是"改那一张"。

## 技术特性

- **零依赖** —— 纯 Python 标准库（`struct` / `json` / `pathlib`），手写 PNG / JPEG / GIF / TIFF 头部解析。不需要 Pillow，不需要任何 `pip install`
- **原件只读** —— 永不修改、移动、重命名、删除输入文件
- **Python 3.8+** —— 跨平台，Windows 控制台编码已处理

## 触发边界

**不触发**：

- 需要内容合规审查（本插件做不到）
- 要生成新内容或图表（那是出图技能的事）
- 只问平台通用规则而没给具体文件
- 需要实际执行格式转换并落盘产物（只诊断，不代改）
